Why a shared library

  
Instead of every team copying and drifting its own Jenkinsfile, each concern is one step that every pipeline calls the same way.

  

    
1
Build and test
buildPython installs dependencies, lints with flake8, runs pytest with coverage and fails the build when coverage drops below your threshold.

    
2
Ship
dockerBuildPush pushes the commit SHA and latest tags. deployK8s applies the manifests, watches the rollout and rolls back on timeout.

    
3
Tell people
notifySlack and notifyTeams post color-coded status. llmAnalyzeFailure sends the log tail to an OpenAI model and posts a root-cause guess to Slack.

  






  
Tests 

  
Read from the repo's JenkinsPipelineUnit specs on every deploy. Specs exist for buildPython, deployK8s, notifySlack and notifyTeams. dockerBuildPush and llmAnalyzeFailure have none yet.

What this does not do
    
    
  • The page cannot run a Jenkins build. It generates a Jenkinsfile from the real step parameters.
    • 
    
  • The surrounding stages and the post blocks come from the README's example pipeline, not from the library itself.
    • 
    
  • llmAnalyzeFailure calls the OpenAI chat completions API, needs a secret-text credential and curl on the agent, and its output is a guess to verify.
    • 
    
  • The repo has no Gradle wrapper checked in, so running the specs needs a local Gradle.
